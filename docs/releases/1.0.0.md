# AniProject 1.0.0 — launch release

Released 26 October 2026. One coordinated release for AniHome, AniBrave for Android, the AniBrave desktop extension, and the shared banner catalog.

## A single version and a complete download

This launch establishes **1.0.0** as the shared product version. AniHome, the Android browser, and the desktop extension all report that version. Their Android upgrade codes increase independently so existing installations can be updated safely: AniHome uses code **45**, and AniBrave Android uses **429705625**. The separate Brave engine identifier is **1.98.60**, with Chromium **156.0.8078.48**; that upstream identifier is not the AniProject product version.

The launch collects the completed features and maintenance fixes from the pre-launch builds. It does not introduce a different browser engine, replace the existing signing identities, reset application data, or turn synthetic test coverage into a claim of universal device or streaming compatibility. The feature set below describes the software actually included in the release.

## AniHome: a wallpaper-first Android home screen

AniHome is an Android launcher with apps, website shortcuts, banner artwork, compact app icons, and widgets on the system wallpaper. It can be selected as the default Home application. It does not require the browser to be open to show installed apps or the Home layout. Website shortcuts retain their originating application and destination rather than being rewritten into generic app launches.

An empty Home remains empty: there is no message demanding that apps or widgets be added. The wallpaper stays visible. Adding content is a deliberate action available through Home editing and app-drawer actions. The layout supports phones and tablets; landscape uses a side dock, while portrait can use the compact bottom arrangement. Home hides its status bar while leaving Android system navigation available.

### Banners, compact icons, and custom artwork

Native applications and websites can appear as wide banner tiles. App tiles can also be changed to compact app-icon presentation from their contextual menu. Switching presentation retains the tile's saved artwork, so returning to a banner does not require choosing the image again. Names can be shown or hidden, and tile labels can be renamed locally without changing the installed application's actual name or a shortcut's original destination.

A newly added application tile can use a matching public-catalog banner automatically when an exact package match is available. Otherwise, it falls back to application artwork. A manual image choice or reset takes priority over a late automatic result for the lifetime of that Home tile. Existing tiles retain their selected artwork; a catalog refresh is not permission to overwrite a customized Home screen.

The image picker supports the bundled Banner Store and personal image selection with cropping. Artwork loads and cache misses are handled off the main UI thread. Refreshes discard stale work instead of allowing an old response to replace a newer selection. Shared artwork and notification-tag clipping prevent the banner's color from bleeding around a separately antialiased corner tag.

### Editing, rearrangement, and removal

Hold a tile or widget and drag to move it. Holding a tile still provides its contextual actions. A long press on empty Home enters editing; tapping empty Home or the dock's confirmation control finishes editing. The Add control is shown in edit mode rather than occupying the ordinary dock permanently. An optional layout lock prevents accidental edits.

Banners, compact icons, and widgets use one persistent cell board. Widgets can sit beside or between tiles rather than being confined to a separate widget section. Intentional placements survive ordinary reloads. Removing items compacts the remaining board in visual order, bringing lower items forward instead of leaving them stranded below a large deleted region. Ordinary tile removal offers Undo; removal does not uninstall the underlying application.

Floating remove controls overlap the corner with a neutral glass treatment. Their touch areas remain usable, labels have sufficient layout height, and ancestor clipping no longer cuts off the corner control. Added tiles return to full opacity across artwork refreshes, edit-mode changes, and view recycling. Dragging is bounded to the visible scrolling area and follows the pointer during edge scrolling. Drop placement is committed without a return-to-origin recovery animation.

### Widgets and notes

AniHome supports Android provider widgets and built-in **Clock & date**, **Battery**, and **Quick note** widgets. Provider availability and configuration remain governed by the installed provider application. Existing provider views are retained across ordinary refreshes rather than unnecessarily rebuilding live widgets.

Resize widgets from their edges while editing. Hold the center to rearrange them on the shared board. The visible editing control is Remove; resize behavior is not hidden behind an extra row of unexplained buttons. Widget content uses consistent gutters, and the earlier editing hint overlay has been removed. Notes stay local, and interrupted note drafts can be recovered. Widget-size limits still respect the provider and available cell geometry.

### App drawer, favorites, recent files, and search

The drawer refreshes its app discovery when opened and observes package changes while running. Newly installed apps can therefore appear without restarting the launcher. The grid adapts to available width and text geometry so icons and labels are not forced into tablet-sized cells on a phone.

On tablets, Recent files occupies the left area. The wider application area has a horizontal Favorites row above its independently scrolling All applications grid. Portrait tablet application layouts retain four columns where the tablet layout applies. Phone layouts use an adaptive full-width app grid, separated app suggestions on taller screens, and an integrated Recent files handle/header. Expanding Recent files gives it roughly half the usable screen rather than forcing a small target against the system gesture area.

Recent files uses Android media/document access and previously authorized locations. Entries can be opened, shared through Android's chooser, or inspected for file information. Selecting Share opens a chooser; it does not silently send a file. Availability depends on Android permissions, indexing, and document-provider access, so this is not a promise to list every private file owned by every application.

Search filters apps and accessible files and visibly offers a browser/address action. The selected dock browser is used when appropriate. The launcher does not hide web search behind an unexplained Enter-only behavior. App actions include adding to Home, hiding/restoring drawer entries, opening App info, and requesting uninstall. Batch additions preserve existing tiles. Hiding an app from the drawer does not uninstall it or remove its Home tile.

### Dock appearance and useful status

The dock contains the clock/date area, search/browser entry when enabled, the application-menu control, optional Recents access, notifications, and as many chosen app pins as the current layout permits. Pin capacity follows the space available. Pinned application artwork uses a consistent circular mask; the app-menu control uses solid grid blocks inside a transparent outlined circle.

The time and date are grouped compactly. Battery percentage is visible with the battery icon; battery color is red at 20% or below, yellow from 21–49%, and green from 50%. Active charging uses a separate visible charging bolt. The USB indicator is hidden when USB is disconnected. Side and bottom dock arrangements account for their different available space.

Choose a browser for the dock entry and its corresponding icon, hide or show the search entry, and independently hide or show the Recents button. Gesture assignments remain available when the button is hidden. Dock background opacity can follow wallpaper contrast dynamically or use a manual 0–100% slider. The outline remains distinct when the black background tint becomes transparent; opacity changes do not fade the text, icons, and border together.

### Notifications and inline quick controls

The notification sidebar attaches to the left screen edge and can be opened from its dock control, the clock/date area, or an assigned gesture. Tap outside to dismiss it. There is no confusing top close button next to Clear all. Compact headings and app rows preserve space for actual notification content. App-icon and banner badges display contrasting counts; the dock notification control provides a separate indication of waiting alerts.

Notifications support expansion/collapse, available notification actions, dismissal, and Clear all. Cancellation is reconciled against Android's active notifications. Ongoing or protected alerts are not falsely treated as removable. Removing the final clearable child also handles a dismissible group summary, and stale expanded state is discarded. Notification options include Android notification settings and one-hour snoozing when Android permits it. Notification access is optional.

Wi-Fi, Bluetooth, rotation, and Home settings share the sidebar. Wi-Fi and Bluetooth expand inline with labeled sections, refresh controls, power toggles, and scrollable results rather than opening a separate floating selection window. Connected and recently used devices are prioritized. Searching, requesting a connection, pairing, and successfully connecting are distinct operations; a request is not presented as proof of a successful association.

Direct radio operations use optional Shizuku access. Android permission requirements, Location requirements for relevant scans, pairing confirmation, Bluetooth profiles, saved-network credentials, and system restrictions still apply. Advanced radio options can open Android's own settings. AniHome does not persist Wi-Fi passwords; Android manages saved network credentials. Scan lists are not uploaded.

Opening Notifications after visiting Home settings now starts in Notifications. Returning from an external settings screen or restoring a configuration explicitly retains the appropriate selected section. This separates a fresh notification entry from restoration of work already in progress.

### Gestures, motion, and rotation

Assign up, down, left, and right swipes independently. Default assignments differ between phones and tablets; saved choices are retained. A double tap on empty Home can lock the screen through the optional Accessibility control. Long press enters editing, and double-tap locking is suppressed during editing. Recents and lock actions require the corresponding Android capability rather than being simulated by clearing apps or turning the display black.

Vertical swipes scroll Home when there is content left in that direction, including the swipe that reaches a scroll boundary. They do not unexpectedly become a launcher gesture while the same scroll is in progress. Drawer and sidebar entrance direction follows the invoking gesture. Expansion and notification removal use short motion, and Android's reduced-motion/animator preference is respected.

Entrance animations now own and clean up their pending pre-draw and frame callbacks. Replacement, cancellation, and detachment complete once, restore opacity/translation, and release pending drawer loads. An interrupted entrance no longer leaves an invisible view or blocks later updates indefinitely. This repair is specifically exercised by repeated navigation and cancellation tests.

Rotation has two behaviors: **Auto** and **Fixed**. Fixed captures the visible angle through Android system settings; Auto returns control to Android's rotation behavior. Changing that toggle requires modify-system-settings permission. Opening Home or the drawer does not write a rotation lock. Failed explicit changes roll back instead of leaving half of a setting applied. Old app-only angle preferences are migrated away.

No forced-display-angle service or separate tablet rotation guard is bundled with the launch. Android and individual applications retain their supported orientation policies. A system Fixed choice can remain after AniHome is uninstalled because it is an Android setting; restore Auto-rotate through Android quick settings. Firmware or sensor faults are not resolved by relabeling the launcher version.

## AniBrave for Android

AniBrave is an independent Android browser customization based on the pinned official Brave ARM64 APK. It installs as `app.anibrave.main` alongside official Brave, with its own browser profile. AniHome installs separately as `app.anihome.launcher`. Existing compatible AniBrave updates retain its profile; they do not import cookies or logins from a different installed browser.

The native Brave engine and Shields libraries are retained from the verified upstream package. This project adds locally compiled Java/JavaScript integration and repackages the Android application with its own signing identity. It is not a complete Chromium source build or an official Brave distribution. Standard browser features and privacy services retain their own upstream behavior and settings.

### Browser tools and per-site viewing

A sliders control beside the native tab switcher opens the AniBrave feature menu. It includes Playback speed, Site view, Fullscreen shortcut, Watched anime, Streaming buffer, and tab-layout settings where applicable. Ordinary website seeking, subtitles, audio language, and player controls stay available.

Site view choices are **Mobile**, **Desktop identity · mobile layout**, and **Desktop**. Choices are stored per site and reload the page. Rotation updates the viewport geometry. Device identity and layout are different controls: changing identity does not guarantee that a site will choose a particular design, and account settings or server-side redirects can still affect the result.

The native tab layout can use horizontal tabs or a collapsible vertical sidebar. The vertical layout provides counts, compact rows, Regular/Private switching, and tab actions while preventing the ordinary horizontal compositor strip from reappearing during toolbar/scroll changes. Layout geometry accounts for portrait/landscape and available space. The launch includes the previous native-tab visibility, selection, and sidebar refinements.

### Playback speed synchronization

Android playback choices include **0.5×, 0.75×, 1×, 1.25×, 1.5×, 1.75×, 2×, 2.5×, 3×, and 4×**. Choices are saved per website; ordinary `www` and bare-host aliases share their setting. Embedded playback uses the relevant top website setting. A replacement player or a new episode can reapply the saved choice.

The site player's deliberate speed selection and AniBrave's control synchronize in both directions where the player is accessible. Native acknowledgements are handled without letting a stale response overwrite a newer choice. Bounded recovery handles scripted startup resets without continuously fighting the page. Explicit rates beyond a site's own menu can use accessible HTML media playback when the native player API refuses the rate; a menu that cannot display that rate may still lack a corresponding item.

Ad playback, detached media, unsupported players, and genuine user controls are treated separately. The feature does not replace the website player, subtitles, or DRM session. A protected player can still reject script access or the desired rate. The Android and desktop products share the synchronization approach but expose different selectable ranges.

### Immersive website shortcuts

Create a fullscreen shortcut from AniBrave's feature menu and confirm the launcher prompt. AniHome supports Android's pinned-shortcut flow. A shortcut retains its original destination and extras rather than becoming a generic browser icon. Shortcuts created in another browser remain associated with that browser.

AniBrave shortcuts use its normal browser profile with hidden browser chrome and immersive Android bars. They retain a task root so a shortcut session can participate in Recents instead of disappearing solely because it is the only browser window opened. Tools can be revealed through supported page/scroll gestures, and the feature avoids inserting a permanent floating playback control into the page.

A shortcut can resume the last eligible foreground normal-profile URL for its site. Private and background pages do not replace that saved destination. The website still controls its own login, subscription, fullscreen capabilities, and media behavior. An immersive shortcut is a browser session, not an independently packaged website application or an offline copy.

### Streaming buffer and stall handling

The Streaming buffer control applies across normal browser tabs and immersive shortcuts. It offers Site default or a request for one, three, five, or ten minutes ahead; the default request is three minutes. Accessible matching HLS.js and Shaka players can receive a larger forward-buffer goal, while ordinary media receives its existing preload hint without changing the source or seeking ahead.

The request preserves quality selection, authentication, encrypted-media sessions, and the site's existing loader. Recognized ads, live media, and unrelated player instances are excluded where detected. Site default restores supported original goals. A player can hide its API, cap downloads, or stop fetching while paused; the chosen target does not guarantee full-episode loading.

Optional Buffer guard responds to a finite video that stalls while playing. It owns only its temporary pause, waits for a practical playback cushion, and can resume that pause when useful buffering is available. Trusted input, seeking, navigation, source changes, or hiding the page cancel stale resumption. Deadlines and cooldowns bound retries. It does not lower quality automatically, invent bandwidth, or create a persistent downloaded media file.

## Episode memory and cross-site continuation

AniBrave Android and the desktop extension maintain local episode memory in their respective installations. There is no shared cloud account or automatic synchronization between the Android browser and the desktop extension. Each browser profile controls its own history and site preferences.

Supported automatic identity adapters include Crunchyroll, HiAnime, and AniKoto watch pages. Titles, seasons/parts, and episode numbers are treated distinctly. HiAnime's internal `ep` query identifier is not assumed to be an episode number. Missing or ambiguous identity requires manual confirmation rather than guessing a remote catalog ID.

### Recording genuine progress

Opening a page can display an existing offer, but opening alone does not count as watching. Automatic memory requires at least 15 seconds of actual advancing playback on accessible qualifying video. Pauses, buffering, seek jumps, known ads, and short media do not create watched coverage. Embedded media can supply progress while the top watch page supplies the identified episode.

The episode archive separates a series' most recent summary from individual seasons, parts, and episodes. It preserves the latest position and unique watched intervals. Completion is based on at least 85% observed coverage and remains recorded during later rewatches. Seeking near the end does not itself prove completion, and watching an earlier episode does not erase a completed later episode.

### Continue here, search, and explicit confirmation

A continuation offer shows the saved series, episode, timestamp, and source. Continue here first uses a learned exact target URL when available. Otherwise it uses a supported search adapter or a suitable same-origin GET search form. A unique exact-title result and an unambiguous matching episode can be followed. Ambiguous seasons, translations, numbering differences, missing links, or unsupported search forms remain manual.

Confirming the episode can learn a local title alias, numbering offset, and exact URL for later use. Open previous site returns to the saved source episode. Done or dismissal clears the relevant handoff/presentation without erasing the episode archive. Ordinary repeated progress does not repeatedly revive an already dismissed offer for the same episode; a different episode can produce a new offer.

An explicit handoff is time-bounded rather than an indefinite instruction to keep navigating. On Android it belongs to the relevant native tab and can survive eligible navigation/reload within its 30-minute lifetime. Exact episode confirmation and accessible, sufficiently long, seekable media permit position and saved-speed restoration. Playback is not forced to start. Unsupported or restricted media retains manual guidance.

### History navigation and retained players

Back and Forward are user navigation. Traversal and BFCache restoration pause automatic continuation routing so a search → series → episode flow does not trap the user by immediately forwarding again after Back. An explicit new continuation request can start a new handoff.

A new explicit resume invalidates previous seek markers on a retained single-page player. Returning through history therefore does not reuse an old successful-seek flag and ignore a new request. A newer saved timestamp for the same episode is honored. Navigation, replacement media, visibility, and trusted seek actions cancel stale pending work where appropriate.

### Editing and preserving local history

The library supports local corrections and deletion controls. Android provides its episode archive and dated legacy watch-log access; the desktop extension provides its local episode-memory interface and manual entry. Forgetting an entry removes its associated episode/season information as implemented, rather than leaving a reminder disconnected from its archive.

Partial structured metadata updates retain missing identifiers instead of erasing known episode fields. Correcting an episode identity preserves explicitly learned cross-site links and metadata in a transaction. A failed transfer rolls back rather than leaving a half-moved record. Empty normalized series identities are rejected to avoid collisions between punctuation-only labels.

Private Android tabs neither read nor write normal continuation history, and native presentation is removed across the corresponding profile transition. In the extension, episode history is hidden and history-writing actions are blocked in private windows. Playback/view preferences remain shared where documented; private-window mode is not described as a separate secret settings profile.

## AniBrave desktop extension

The desktop product is an unpacked Manifest V3 extension for Brave. Its popup provides playback-speed controls, one website-view selector, and a collapsible Episode memory area. No Android APK is needed to use it. It is delivered as a ZIP rather than an extension-store installation.

### Desktop playback and website views

Desktop speed uses **0.25× through 5× in 0.25× steps**. Site and extension selections synchronize where the player is accessible, including an open popup. An explicit extension rate can take precedence when the site menu refuses it; a genuine subsequent site speed-control choice becomes the new saved choice. Known ad playback does not overwrite that preference. New videos, later metadata, frames, reloads, and replacement players are handled without a permanent rate-reset loop.

Long HTML audio is supported, while clips under 20 seconds are excluded from ordinary speed application. Rates outside the extension's range remain the site's responsibility. The feature discovers supported embedded and shadow-root media, but browser internal pages, inaccessible frames, protected players, and browser security boundaries remain restrictions.

Desktop view restores ordinary identity and layout. Mobile view combines an Android phone identity, touch emulation, and a 412 × 915 viewport. Mobile identity changes identity while retaining a desktop-sized viewport. Each site's choice is stored independently. Emulation is per tab, and a restored browsing session can reapply saved choices on navigation.

Brave displays a debugger notice while the emulated modes are attached. Opening DevTools or canceling that connection can interrupt emulation; selecting the mode again can restore it. The first request in a newly opened tab can precede application of a saved mode, and a website may require reload or use its own layout rules. The tested mobile layout reaches 412 pixels; emulation does not turn the PC into a physical phone.

### Desktop setup and updates

Extract `AniBrave-Extension-1.0.0.zip` to a permanent folder. In `brave://extensions`, enable Developer mode, choose Load unpacked, and select the folder containing `manifest.json`. Pin the toolbar entry if desired, then reload websites that were already open before installation.

For an existing unpacked installation, update the files in the same loaded folder and press Reload on its extension card. Reload open player pages afterward. Keeping the same loaded folder preserves the installation's identity and local storage in the usual unpacked-extension workflow. Uninstalling the extension removes its storage. The GitHub release does not silently replace the files in a separately loaded local folder.

## Banner catalog

The shared catalog contains **177 entries**, with reviewed app identities, package/alias matching, provenance, and checksums. It includes the additional system and Lineage application variants and corrected artwork for brands such as Apple TV, Grok, Grok Bot, Opera, X, LinkedIn, Udemy, ZEE5, SonyLIV, and Shizuku. Complete wordmarks are used without unnecessarily repeating the same app name beside them. RawCam deliberately uses the selected Pixel Camera visual substitute; provenance distinguishes that choice from RawCam's upstream icon.

AniHome bundles the catalog for offline use and can Refresh anonymously from the independent public repository. No GitHub account or token is required. Downloads retain path/host checks, bounded sizes/dimensions, and SHA-256 verification. A failed refresh preserves the existing bundled/cached artwork. Catalog curation is not a live app-store popularity ranking or a claim of endorsement by the respective brands.

## Permissions, privacy, and data boundaries

Notification access is required only for notification display/counts and related actions. Optional Accessibility access enables supported Recents and screen-lock actions; it does not request screen-content access. Modify-system-settings permission is relevant to the explicit rotation toggle. Wi-Fi/Bluetooth operations can require runtime permissions, system Location, pairing approval, and optional Shizuku authorization. File features depend on media/document permissions and selected folders.

Launcher tiles, custom names, notes, app frequency, and connection recency stay local. Notification content remains in memory and is not uploaded or archived by AniHome. The launcher does not persist scanned Wi-Fi lists or Wi-Fi passwords. The custom browser episode archive and extension history stay in their respective private application/profile storage; there is no project cloud-history service or cross-device synchronization account.

These local-data statements apply to the custom features. Ordinary web browsing, the upstream browser's configured services, website requests, and anonymous banner refreshes still involve network communication. The public release contains project source and assets, not personal conversations, installed-device inventories, private credentials, signing keys, or a local tablet configuration/rotation guard.

## Installing and upgrading the Android apps

Install the AniHome and AniBrave APKs individually or extract them from the combined bundle. Android may require installation permission for the app opening the APK. Choose AniHome as the Home application if it should replace the system launcher. AniBrave can coexist with official Brave; install the correctly named package rather than replacing an unrelated browser.

Install matching signed updates over existing installations. Do not uninstall or clear data merely to update. Both original project signing identities are retained, and Android build codes increase above the preceding releases. User layouts, notes, shortcuts, browser profiles, and episode history are intended to remain in place. Existing website subscriptions, logins, and permissions remain subject to Android and the site.

Notification, file, Accessibility, modify-system-settings, and Shizuku permissions are optional feature-specific setup, not a blanket requirement to start the launcher. If a radio scan is empty, verify the relevant Android permissions and service state before assuming a device is absent. If a protected notification cannot be removed, Android may intentionally require it to remain visible.

## Known limits and support scope

- AniBrave Android is ARM64 and Android 10+; AniHome supports Android 8+. No new Linux desktop browser, iOS app, or revival of the retired AniBrowser Full/Lite variants is included.
- Protected/DRM players, native closed players, site markup changes, ads, subscription rules, and regional catalogs can restrict speed, seeking, identity detection, and continuation. The launch does not bypass access controls or DRM.
- Buffer targets are requests. Sites, memory limits, live media, and connection throughput can prevent the requested amount from being buffered.
- Device firmware can affect widgets, rotation, navigation, Bluetooth profiles, Wi-Fi scans, and system permissions. Android orientation policies remain authoritative; there is no forced global angle service in this launch.
- A selected Android system rotation lock can remain after uninstall. Enable Auto-rotate in Android if a system Fixed setting is no longer wanted; a separate sensor or firmware problem requires separate diagnosis.
- Desktop view emulation can be interrupted by debugger cancellation or DevTools. Site identity and visible layout are related but not equivalent.
- Public release verification does not imply that every live signed-in streaming service or every physical phone/tablet configuration has passed acceptance. No universal frame-rate, bandwidth, or animation-smoothness guarantee is made.
